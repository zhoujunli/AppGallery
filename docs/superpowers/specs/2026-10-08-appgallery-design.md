# AppGallery 设计规格

> 日期：2026-10-08
> 状态：待评审

## 1. 目标

一个展示个人做过的项目的网站，同时提供安装包下载。

**定位**：对外展示为主，兼顾分发。访客是招聘方、同行、朋友 —— 他们来看"你做过什么"，顺手下个安装包体验。

**成功标准**：

- 访客能在 10 秒内理解这个站是干什么的，并找到一个感兴趣的项目
- 从首页到开始下载，不超过两次点击
- 新增一个项目只需改一个文件 + 放一张图
- 发布一个新版本不需要改动网站代码
- 静态托管在阿里云 OSS，绑定已备案的自有域名

**非目标**（明确不做，见第 11 节）：后台管理、站内搜索、多语言、访问统计。

## 2. 关键决策一览

| 决策点 | 结论 |
|---|---|
| 页面数量 | 2 个内容页（首页 + 项目详情页）+ 1 个 404 页 |
| 布局 | Hero + 卡片网格 |
| 视觉风格 | 暗色科技感（默认）+ 浅色模式，共用同一批组件 |
| 主题切换 | 三态循环：跟随系统 → 浅色 → 深色，选择存 `localStorage` |
| 卡片在无截图时的撑法 | 图标 + 项目主题色渐变 |
| 平台 | Android、桌面端（Win/macOS）、Web |
| 素材 | 只有文字 + App 图标，无截图、无视频 |
| 源码托管 | 阿里云 Codeup |
| 网站托管 | 阿里云 OSS 静态网站托管 + 已备案自有域名 |
| 安装包托管 | GitHub Releases，**仅此一处** |
| 部署方式 | 云效流水线，`ossutil` 上传 |
| 版本信息来源 | 构建时由流水线调 GitHub API 生成 `versions.json` |
| 前端调用 GitHub | **否**（仅在访客点下载时跳转 GitHub） |
| 构建步骤 | 无前端构建，只有两个 Node 脚本（零依赖） |

## 3. 页面结构

### 3.1 首页 `index.html`

自上而下五块：

1. **顶栏** —— 左侧品牌标识（渐变方块 + "AppGallery"），右侧导航链接和主题切换按钮
2. **Hero** —— 一枚状态徽章（"N 个项目 · 持续更新"）、一行主标题、一句说明
3. **筛选条** —— 全部 / Android / 桌面端 / Web
4. **卡片网格** —— 项目卡片
5. **页脚** —— 版权、GitHub 链接

### 3.2 详情页 `project.html?p=<项目id>`

1. **顶栏**（同首页）
2. **返回链接** —— "← 全部项目"
3. **项目头部** —— 大号图标、项目名、一句话简介、平台标签
4. **下载区** —— 主下载按钮 + 历史版本列表
5. **介绍区** —— "关于这个项目" 段落、"技术栈" 标签、"相关链接"
6. **页脚**（同首页）

桌面端下载区与介绍区左右两栏（约 1.35 : 1），窄屏改为单栏上下堆叠。

**"相关链接" 的内容**，只有这两项，缺哪项就不渲染哪项：

- **Releases 页 ↗** —— 由 `releasesRepo` 拼出 `https://github.com/<owner>/<repo>/releases`。**指向成品仓库，不是源码仓库**（源码不开源，指向私有仓库会 404）
- **在线体验 ↗** —— 由 `liveUrl` 提供，可选

### 3.3 404 页 `404.html`

一个极简页面：一行"没找到这个页面"、一个回首页的链接，沿用同一套配色。OSS 静态网站托管的默认 404 指向它。

### 3.4 导航链接

只保留「项目」和「GitHub」两项。GitHub 指向你自己的主页（`https://github.com/<你的用户名>`），不是某个仓库。

**不做独立「关于」页** —— 自我介绍放在首页页脚上方一小段。若后续觉得需要，再单独开页。

## 4. 数据模型

### 4.1 手写配置 `projects.js`

```js
window.PROJECTS = [
  {
    id: "tide-focus",                       // 详情页地址 ?p=tide-focus，必须唯一
    name: "潮汐番茄钟",
    tagline: "安静到不像效率工具",            // 卡片上的一行
    description: "番茄钟我试过十几个……",      // 详情页段落，字符串或字符串数组
    icon: "icons/tide-focus.png",           // 相对路径，可省略
    theme: ["#6366f1", "#8b5cf6"],          // 渐变两端色值，一般取图标上最深和最亮的两个色
    platforms: ["android", "web"],          // android | desktop | web | miniprogram，可多选
    stack: ["Kotlin", "Compose", "Room"],   // 技术栈标签
    releasesRepo: "xj/tide-focus-releases", // 可选，GitHub 公开仓库，owner/repo
    liveUrl: "https://tide.example.com"     // 可选，在线体验地址
  }
];
```

**数组顺序即首页排列顺序**，不做自动排序 —— 哪个项目放前面是人的判断。

**`platforms` 与 `releasesRepo` 是两件事**。`platforms` 说这个东西能装在哪，`releasesRepo` 说版本号去哪拿。小程序（`miniprogram`）两样都没有：装不了，也没有 GitHub Releases。所以两个字段都是可选的，缺了就不渲染对应的那部分 —— 缺 `releasesRepo` 不画「Releases 页」按钮、卡片上也不写版本号，而不是拼一条 `github.com/undefined/releases` 的死链。

**用 `.js` 而非 `.json`**：`fetch()` 读本地 JSON 会被 CORS 拦截，导致双击 `index.html` 打不开。写成 `<script src="projects.js">` 挂全局变量则没有这个限制。

### 4.2 自动生成 `versions.json`

构建时由流水线生成，与网站文件一同部署到 OSS 根目录：

```json
{
  "tide-focus": [
    {
      "version": "2.1.0",
      "date": "2026-09-28",
      "size": "8.4 MB",
      "platform": "android",
      "sources": [
        {
          "label": "GitHub",
          "url": "https://github.com/xj/tide-focus-releases/releases/download/v2.1.0/tide-focus-2.1.0.apk"
        }
      ]
    }
  ]
}
```

`sources` 是数组，第一条为主来源。目前每个版本只有一项。**保留数组形态是为了留后路**：将来若要把安装包搬到 OSS 以改善国内下载速度，只需往数组里加一项，前端逻辑无需改动。

### 4.3 从 Release 里识别安装包

按扩展名归类，认不出的一律忽略：

| 扩展名 | 平台 |
|---|---|
| `.apk` | android |
| `.exe` / `.msi` | desktop（Windows）|
| `.dmg` / `.zip` | desktop（macOS）|
| `.aab` | 忽略 —— 那是给应用商店的，装不上 |
| 其他 | 忽略 |

你发布 release 时不需要遵守命名规范，只要扩展名正确。

### 4.4 数据来源的边界

- **手写的（`projects.js`）**：项目身份、文案、图标、配色、平台、仓库地址
- **自动生成的（`versions.json`）**：版本号、日期、大小、下载链接

**两处不重叠**，所以不会出现"配置文件里写的版本号和实际 release 打架"的情况 —— 版本信息只有 GitHub 一个源头。

## 5. 视觉设计

### 5.1 色彩

一套 CSS 变量，两套取值。深色挂在 `:root`，浅色覆盖在 `[data-theme="light"]`。

| 变量 | 深色（默认） | 浅色 | 用途 |
|---|---|---|---|
| `--bg` | `#0b0d12` | `#ffffff` | 页面底色 |
| `--panel` | `#14171f` | `#ffffff` | 卡片 / 面板 |
| `--border` | `#232833` | `#e8eaef` | 描边 |
| `--text` | `#e8ecf4` | `#0f1115` | 主文字 |
| `--muted` | `#8b93a7` | `#5b6274` | 次要文字 |
| `--dim` | `#4b5163` | `#9aa1b2` | 极次要文字、版本号 |
| `--shadow` | `none` | `0 1px 3px rgba(16,24,40,.05)` | 卡片投影 |

品牌渐变两套主题共用、固定不变：`--brand-a: #6366f1`、`--brand-b: #d946ef`。
`linear-gradient(135deg, var(--brand-a), var(--brand-b))` 用于品牌标识和标题强调。

**每个项目的 `theme` 渐变同样两套主题共用，不重新取色** —— 颜色来自项目图标本身，不随主题变。这是这套卡片设计的关键性质。

### 5.1.1 浅色下必须单独调的三处

浅色不是深色反色。以下三处若照搬深色的做法，观感会坏：

1. **卡片加一层 `--shadow`**。白卡片摞在白底上，没有投影边界会糊成一团。
2. **图标底由深色方块换成白色方块**（`#fff` 底 + `--border` 描边），图标字形用该项目的 `theme[0]`。
3. **Hero 光晕由"发光"降级为极淡水洗**：
   `radial-gradient(60% 90% at 16% 0%, rgba(99,102,241,.10), transparent 70%)`，
   第二层同理、用品牌终点色、透明度 `.08`。深色下的强光晕在浅色背景上会变成一块脏斑。

Hero 的状态徽章在浅色下另用一组：底 `#f5f3ff`、描边 `#ddd6fe`、文字 `#4f46e5`。

### 5.2 卡片

```
┌─────────────────────────────┐
│  渐变条（theme 两端色）      │  ← 桌面 76px / 手机 54px
│  ┌────┐                     │
│  │图标│  ← 下沿压住渐变条边界 │  ← 桌面 44px·圆角 12px / 手机 36px·圆角 10px
│  └────┘                     │
│  项目名                      │
│  一句话简介                  │
│  [平台标签]  v2.1.0          │
└─────────────────────────────┘
```

- 圆角 14px，描边 1px `--border`，底色 `--panel`，浅色下另加 `--shadow`
- 整张卡可点击，进入详情页
- 无截图，所以渐变条是卡片的视觉主体；**图标本身充当"封面"**
- 图标缺失时，用 `theme[0]` 作底色、白色项目名首字作内容，自动生成占位图标。占位图标的底色来自项目主题色、与页面主题无关，所以两套主题下表现一致

### 5.3 响应式断点

| 屏宽 | 卡片列数 |
|---|---|
| ≥1024px | 3 |
| 768–1023px | 2 |
| <768px | 1 |

内容区最大宽度 1120px；桌面左右内边距 20px，手机 14px。

### 5.4 字体

- 正文：`-apple-system, "PingFang SC", "Microsoft YaHei", sans-serif`
- 版本号、编号、标签：`"SF Mono", Menlo, Consolas, monospace`

### 5.5 无障碍

- 所有可交互元素有可见的 `:focus-visible` 描边
- 正文对比度不低于 4.5:1
- 图标 `<img>` 带 `alt`；仅有装饰作用的渐变条用 CSS 实现，不进 DOM
- 卡片用 `<a>` 而非 `<div onclick>`，保证键盘可达和右键新窗口打开

### 5.6 移动端

- **不做汉堡菜单弹层** —— 导航只有两个链接，直接横排
- 筛选条横向可滑，不换行
- 详情页两栏改单栏

### 5.7 主题切换

三态循环：**跟随系统 → 浅色 → 深色 → 跟随系统**。

- 顶栏右上角一个 30px 圆角方块按钮，**图标本身就是当前状态**：`◐` 跟随系统 / `☀` 浅色 / `☾` 深色。不弹菜单。
- 选择存入 `localStorage`。
- `跟随系统` 状态下监听 `prefers-color-scheme` 变化并实时响应。
- 按钮带 `aria-label`，值形如"当前：跟随系统，点击切换"。

**必须避免首屏闪烁（白闪）。** 主题要在 CSS 绘制前就定下来，所以判断逻辑用一段**内联在 `<head>` 里的小脚本**实现，`index.html`、`project.html`、`404.html` 三个页面各放一份。

**这段逻辑不能放进 `app.js`** —— 那是延迟加载的，会晚于首屏绘制，导致深色系统用户刷新时先白闪一下。

内联脚本只做四件事：读 `localStorage` → 判断是否跟随系统 → 把 `data-theme` 写到 `<html>` 上 → 结束。不引外部文件、不发请求。

## 6. 下载逻辑

### 6.1 主按钮选哪个文件

按访客操作系统挑最合适的那个：

| 访客系统 | 选中的包 |
|---|---|
| Android | `.apk` |
| Windows | `.exe` / `.msi` |
| macOS | `.dmg` / `.zip` |
| 没有匹配的包，或系统判断不出 | 最新版本里的第一个可下载项 |

按钮上写明版本号、大小、日期，让访客知道自己在下什么。

### 6.2 纯 Web 项目

若某项目的 `platforms` 只含 `web`，详情页的下载区整体替换为一个「在线体验」按钮，指向 `liveUrl`。

### 6.3 历史版本

- 默认显示最近 5 个，超出折叠为"展开全部"
- 只有一个版本时，该区块不渲染
- 每行：版本号、日期、大小、下载链接

### 6.4 多来源呈现

`sources` 数组第一条做主按钮。若存在第二条及以上，在按钮下方以一行灰色小字呈现（如"海外访问？从 GitHub 下载 ↗"）。当前只有一个来源，这一行不会出现。

## 7. 异常与降级

**总原则：手写的信息永远在线，自动生成的信息只是增强。** 拉不到就退回朴素形态，不白屏、不转圈、不弹错误框。

| 情况 | 表现 |
|---|---|
| `versions.json` 加载中 | 卡片正常显示，版本号位置是一条灰色脉冲条 |
| `versions.json` 加载失败 | 卡片显示"版本信息暂不可用"，仍可点进详情页；详情页下载区退化为跳转 GitHub Releases 的按钮 |
| 项目没有任何 release | 卡片不显示版本号；详情页下载区写"还没有可下载的版本" |
| 项目未配 `releasesRepo` | 卡片上连"版本信息暂不可用"也不写 —— 它没有版本号这回事，不能说一个不存在的东西"暂时拿不到"。详情页相关链接里不画 Releases 页 |
| 项目未配 `icon` | 自动生成占位图标（`theme[0]` 底 + 名称首字）|
| 项目未配 `liveUrl` | 相关链接中的该项不渲染 |
| URL 的 `p` 参数不存在 | 显示"找不到这个项目"及回首页链接 |
| 项目数 < 5 | 筛选条不渲染（数量太少时筛选没有意义）|

上表第 2 行（加载失败）是整批的：`versions.json` 一次拉完，拉不到就是所有卡片一起拿不到。所以"未配 `releasesRepo`"那一行必须排在它前面判 —— 否则小程序会因为**别的项目**拉取失败而冒出一句关于版本号的话。

这条优先级在三个地方都用同一个顺序（"有没有仓库"是项目的属性，"拉没拉到"是这一次网络的结果，属性先判）：

1. 卡片的版本号位置（`versionLabel`）
2. 详情页下载区的空态文案（`downloadEmptyText`）—— 没有仓库时永远说"这个项目没有可下载的安装包。"，这句在任何网络状态下都成立
3. 详情页那条"版本取不到"的提示（`shouldShowVersionNotice`）—— 没有仓库时整条不出现，因为那句话里"下载可直接去仓库的 Releases 页"指不到任何地方

## 8. 技术实现与部署

### 8.1 仓库结构

```
AppGallery/                      ← Codeup 仓库
├── index.html
├── project.html
├── 404.html
├── projects.js                  ← 唯一需要手写的数据文件
├── assets/
│   ├── style.css
│   └── app.js
├── icons/                       ← 每个项目一张图
├── scripts/
│   ├── fetch-releases.mjs       ← 构建时生成 versions.json
│   └── validate-projects.mjs    ← 配置校验
├── docs/superpowers/specs/
└── .gitignore                   ← 忽略 .superpowers/
```

无 npm 依赖、无打包、无框架。两个脚本用 Node 内置能力，零依赖。

### 8.2 部署目标（OSS Bucket）

```
bucket（绑定已备案域名）
├── index.html
├── project.html
├── 404.html
├── projects.js
├── versions.json          ← 构建产物
├── assets/
└── icons/
```

Bucket 配置要点：

- 关闭"阻止公共访问"，权限设为**公共读私有写**
- 开启静态网站托管，默认首页 `index.html`，默认 404 页 `404.html`
- 绑定自定义域名并配置 HTTPS 证书（阿里云可申请免费证书）

**注意**：OSS 默认域名访问 HTML 会被强制下载（`Content-Disposition: attachment`），必须通过绑定的自定义域名访问网站。

### 8.3 云效流水线

1. 拉取 Codeup 仓库
2. 运行 `node scripts/validate-projects.mjs` —— 配置有误则中断
3. 运行 `node scripts/fetch-releases.mjs` —— 调 GitHub API，生成 `versions.json`
4. `ossutil cp` 上传 `index.html`、`project.html`、`404.html`、`projects.js`、`versions.json`、`assets/`、`icons/`（**不含 `scripts/` 和 `docs/`**）

**权限**：流水线使用的 AccessKey 必须是 RAM 子账号，仅授予该 Bucket 的读写权限，不使用主账号 AK。

**构建触发**：至少支持手动触发。可选加 GitHub release webhook 实现全自动（需额外配置）。`fetch-releases.mjs` 在拉取失败时必须保留上一次的 `versions.json` 而非写空文件。

### 8.4 前端不做的事

前端**不调用任何 GitHub API**。访客只有在点击下载时才会跳转到 GitHub。这是为了保证国内访客打开页面的速度 —— 页面上的所有资源都来自 OSS。

## 9. 测试策略

没有前端构建，所以测试落在三处：

### 9.1 配置校验脚本

`node scripts/validate-projects.mjs` 检查：

- `id` 唯一且符合 URL 安全字符
- `icon` 指向的文件真实存在
- `theme` 是两个合法十六进制色值
- `platforms` 取值在允许集合内（`android` / `desktop` / `web` / `miniprogram`）
- `releasesRepo` 若存在则符合 `owner/repo` 格式
- `platforms` 只有 `web` 时必须同时给 `liveUrl`（否则访客没有任何入口）
- `liveUrl` 若存在则是合法 URL

配置写错时立刻报错，而不是等页面渲染出来才发现图标裂了。

### 9.2 纯函数单元测试

用 Node 内置 `node:test`（零依赖）覆盖有真分支、最容易写错的逻辑：

1. **扩展名 → 平台映射**（含 `.aab` 和未知扩展名被忽略的情况）
2. **按访客系统挑主按钮**（各系统、以及判断不出的兜底）
3. **从 release 列表里挑最新版本并排序**（含预发布版本、无 asset 的 release）
4. **`releasesPageUrl`**（没配 `releasesRepo` 时返回 null，不拼死链）
5. **卡片预览的归一化**（三种形态各自的上界，超了返回 null 退回素条）
6. **`versionLabel` / `downloadEmptyText` / `shouldShowVersionNotice`**（加载失败 / 没有 release / 没有 `releasesRepo` 三者的区别，以及那条优先级）

这些从渲染逻辑里抽离成纯函数，先写测试。判断"该不该显示"一律在这里做，DOM 层只负责把结果写进节点。

## 10. 日常流程

**发布新版本**
1. 打包
2. 到 GitHub 公开仓库发 release，挂上安装包
3. 触发流水线（或等 webhook 自动触发）
4. 网站自动更新 —— **不需要改动任何网站代码**

**新增项目**
1. `projects.js` 加一段
2. 图标放进 `icons/`
3. 在 GitHub 建好对应的公开 release 仓库
4. 提交 → 流水线自动部署

**修改界面**
改文件 → 提交 → 自动部署

## 11. 明确不做的

以下都是刻意排除的，不属于本期范围：

- **后台管理界面** —— 项目少，手写配置更快
- **站内搜索** —— 项目数量远未到需要搜索的程度
- **多语言** —— 只有中文
- **访问统计** —— 需要额外服务，且非目标
- **评论 / 留言** —— 需要后端和审核成本
- **RSS** —— 早期草稿的页脚里有这项，实现正文中不予保留
- **独立「关于」页** —— 自我介绍放在首页页脚上方
- **自动排序 / 热门排序** —— 顺序由人决定

## 12. 已知代价

诚实地记录这套方案换来的三个代价：

1. **国内访客下载安装包会慢。** 网站本身在阿里云（快），但安装包托管在 GitHub。这是"安装包只放 GitHub"这一决定换来的。缓解办法已预留在数据模型里（`sources` 数组），未来可无痛加一个 OSS 来源。
2. **新增版本信息依赖流水线跑通。** 如果流水线失败或 GitHub API 不可达，网站会停留在上一次的 `versions.json`。这是可接受的 —— 降级后页面依然完整可用，只是版本号不新。
3. **浅色模式是两套配色的长期维护成本。** 每加一个界面元素，都要确认它在两套主题下都成立；`5.1.1` 那三处说明浅色并非深色的机械反色。这是选择支持双主题换来的，不是可以"以后再说"的欠账。
